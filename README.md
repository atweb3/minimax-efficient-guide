# 📘 高性价比使用MiniMax通用攻略

> 适用于：自动化搭建、AI产品开发、代码生成、配置编写等技术任务

**核心原则**  
把 MiniMax 当作 **“能生成代码和配置的资深顾问”**，而不是能直接替你操作电脑或登录你账号的工人。

---

## 一、五步高效工作流

### 第1步：任务拆解，分块确认
- ❌ 避免：一次性支付高积分要求“帮我搭建一个完整的自动化系统”。
- ✅ 推荐：将大任务拆成独立、可验证的小模块，一次处理一个。
  - 示例拆解：① 抓取脚本 → ② Actions配置 → ③ 推送代码 → ④ 部署命令
- 每完成一个模块，**先验证产出是否正确**，再继续下一个。

### 第2步：明确指令格式，要求“最小可行产出”
每次提问时加入约束：
> “请直接输出完整的代码块，语言标注清楚。不要输出解释性文字、问候语或假设性成功报告。”

- ✅ 好产出：完整的 `.yml`、`.js`、`.py` 等代码块
- ❌ 坏产出：“首先你检查一下...”、“我假设你已经成功...”、“你可以去点这个按钮...”

### 第3步：优先使用“免费诊断模式”
- 在支付积分前，要求 MiniMax 输出 **零成本诊断方案**：
  > “请给我一份只需要手动检查的清单，来判断系统哪里出了问题。”
- 你按清单自查，将结果反馈，再让它给出**针对性修复方案**。

### 第4步：拒绝“虚构成功报告”，要求“可验证的产物”
- 若 MiniMax 描述运行结果（如“Run #7 成功，耗时18秒”）但无你提供的截图或日志，**很可能是虚构内容**。
- 应对方法：  
  > “不要告诉我‘成功了’，请直接给我修复后应放在仓库里的完整文件代码。”

### 第5步：自己部署、验证、反馈
- MiniMax **无法登录你的 GitHub、飞书、服务器**，所有实际操作必须由你完成。
- 高效循环：  
  获取代码 → 本地/云端部署 → 手动测试 → 贴错误日志 → 让它迭代修复

## 二、积分控制技巧表

| 场景 | ✅ 推荐做法 | ❌ 避免做法 |
|------|-------------|--------------|
| 初次诊断 | 要求输出“免费自查清单” | 直接付积分让它“全面检查” |
| 生成代码 | 要求“直接给完整文件，不要解释” | 让它边解释边写（浪费积分） |
| 调试错误 | 贴完整日志，要求“只修改必要行” | 让它重写整个文件 |
| 验证成功 | 自己手动触发，不看它的“成功报告” | 相信它说的“运行成功” |

## 三、实战案例回顾（AI Builders Digest 成功经验）

| 你的做法 | 评价 | 改进建议 |
|----------|------|------------|
| 提供仓库、数据源、webhook信息 | ✅ 很好 | 继续保持 |
| 要求输出“诊断指令”而非直接修复 | ✅ 节省积分 | 可进一步要求“只输出代码” |
| 手动触发 Actions 并验证飞书消息 | ✅ 关键步骤 | 必须自己做 |
| 最终收到成功推送 | ✅ 目标达成 | - |

**可优化点**：  
- 在 MiniMax 输出“完整报告”后，你没有直接相信，而是请第三方判断 → ✅ 谨慎  
- 以后可直接要求：“**不要给我状态报告，只给我两个文件的最终代码**” → 省下虚构报告消耗的积分

## 四、适用场景扩展

这套攻略同样适用于：

- 🐍 Python 自动化脚本（数据处理、爬虫）
- 🐳 Dockerfile / docker-compose 编写
- ⚙️ CI/CD 流程配置（GitHub Actions、GitLab CI）
- 📡 API 调用代码生成（飞书、钉钉、Slack 机器人）
- 🤖 简单 AI Agent 或 LLM 应用开发
- 📄 配置文件、脚本模板、正则表达式等

---

## 五、总结

> **把 MiniMax 当成一个“按行收费的代码生成器”，你自己负责部署、测试、反馈。不要为描述性报告或虚构的成功支付积分。**

**每次提问前问自己：**  
👉 “我要求的产出，是我能直接复制、保存、运行的文件吗？”

如果答案是 **“是”** → 可以提交任务  
如果答案是 **“否”** → 先修改指令，要求最小可行产出
